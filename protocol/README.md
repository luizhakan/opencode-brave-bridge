# Bridge protocol v2 — macOS preview

The extension initiates `chrome.runtime.connectNative('dev.opencode.brave_bridge')`.
Chromium native messaging uses a four-byte little-endian length followed by UTF-8 JSON. The host exchanges newline-delimited JSON with MCP processes over a private Unix socket (named pipe on Windows, not yet validated). No TCP listener.

Requests: `{ "v": 2, "id": "opaque", "op": "group.status", "ctx": { "project": "/git/root", "session": "ses_..." }, "params": {} }`.
Responses: `{ "v": 2, "id": "opaque", "ok": true, "result": { ... } }` or `{ "v": 2, "id": "opaque", "ok": false, "error": { "code": "E_...", "message": "..." } }`.

The MCP process derives `project` from its cwd, `session` from OpenCode's `tools/call` `_meta.sessionID`; where unavailable it uses a random identifier scoped to that MCP process. Both values are routing hints, **not authentication** against another process of the same OS user. The extension keys grants by the pair and requires user approval for a dedicated tab group.

Operations:

- `group.status` `{origins?: string[]}` -> `{authorized, project, session, groupName?, tabCount?, origins?, requestedOrigins?, nonce?}`. Requested origins are exact origins (max 20), HTTPS except loopback HTTP. The popup displays the exact session and proposal for explicit confirmation; proposals are not grants and a changed proposal replaces the prior proposal/nonce.
- `tabs.list` `{}` -> `{tabs: [{handle, title, url}]}`; only tabs in this session's group and on approved origins. URL has no query or fragment.
- `tab.snapshot` `{handle}` -> `{title, url, text, elements:[{ref,tag,role,name}]}`; masked secret fields and bounded output, but visible page text can include personal data.
- `tab.open` `{url}` -> `{handle}`; open a new **inactive** tab in the session group's window, only on approved origins.
- `tab.navigate` `{handle,url}` -> `{handle}`; any tab already in the session's group, on approved origins — including the group's currently active tab. Never activates or focuses a tab or window; a navigation of the active tab happens in place.
- `tab.click` `{handle,snapshotId,ref}` -> `{clicked,name}`; a visible element from a fresh snapshot in any authorized tab, including the active tab, after separate per-session/origin **interaction** approval (grant scope `interact-v2`, shared with `tab.fill`). Each snapshot is single-use for clicks, and references expire after 90 seconds; re-snapshot after a click. Synthetic clicks can change account data, but don't provide trusted user activation.
- `tab.fill` `{handle,snapshotId,ref,value}` -> `{filled}`; sets the value of a native text input, textarea, or `contenteditable` element from a fresh snapshot, under the same `interact-v2` interaction approval as `tab.click`. Password, file, hidden, and fields that look like card, token, email, phone, or one-time-code inputs are rejected outright. The typed `value` (max 2000 characters) is never echoed back in the response, and the field is never submitted or sent an Enter keypress. Single-use per snapshot reference, same 90-second expiry as clicks.
- `tab.screenshot` `{handle}` -> image content (JPEG); requires a separate, per-session **visual** grant scoped to one tab handle and one origin (requested via `group.status {requestVisual: true, handle}`, approved from the popup, 30-minute expiry, independently revocable). Approving the request is also what triggers Brave's optional `debugger` host permission prompt — this permission is not requested at install and is released once no session holds an active visual grant. Capture uses the Chrome DevTools Protocol (`Page.captureScreenshot`, `format: "jpeg"`, `quality: 45`) and is re-checked against the live tab/origin/grant immediately before and after the call; the response is rejected if the tab navigated, the grant changed, or the encoded image exceeds 500,000 bytes. **Redaction caveat**: unlike `tab.snapshot`, this is a raw pixel capture — it renders the entire visible surface of the page, including cross-origin iframes, and is not subject to the secret-field masking or text truncation applied to snapshots. Anything on screen (typed values, iframe content, ads) can appear in the image; only grant this for a tab and origin you are fine having captured.

The popup lists pending and approved sessions. The user selects the exact session, previews its proposed origins, then confirms; Chromium's host permission prompt is invoked directly from that click. A new session creates an inactive extension seed tab in its own group without requiring or moving existing tabs. Later requests can propose additional origins, which require a fresh preview and confirmation. Tabs opened by the bridge are inactive and added to that group. Tabs in different groups cannot be addressed by the wrong session.

A grant (read, interaction, or visual) is persisted to `chrome.storage.local` and re-validated whenever the service worker restarts, including after an extension reload: the tab group must still exist with the expected title, its seed tab must still exist at the expected URL, and every granted origin's host permission must still be held, or the stored grant is discarded and the session reverts to needing a fresh approval. A full browser restart always clears every grant, pending proposal, and host permission outright (including the optional `debugger` permission), even though the underlying tab groups remain open; revoking from the popup has the same immediate effect.

## File upload (`upload_file`, in progress)

The MCP `upload_file` tool stages a local `.aab` or `.apk` file and then attaches it to a file input identified by a fresh snapshot, in three explicit steps — **stage, approve, commit**. There is no path from this flow to publishing anything; it only sets the value of a file input.

1. **Stage** — `upload_file` is called with `path` (no `stageId`). The MCP process sends `file.stage` over the local socket. `src/file-stage.js` copies the source file into a per-user staging directory (`XDG_DATA_HOME`/`Application Support`/`AppData` + `opencode-brave-bridge/staging`, `0700`/`0600` permissions) after checking it is a regular file with no hard links or symlinks, matches `.aab`/`.apk`, and is at most 256 MiB. The staged copy lives under a directory named for a random `stageId` (UUID), not a hash of its contents — it is **not** content-addressed storage. A SHA-256 is computed while staging and re-verified against the on-disk file on every subsequent read (`getStage`), which detects tampering or corruption but does not dedupe or address by content. The stage expires after **30 minutes** (`TTL` in `src/file-stage.js`); at most 3 concurrent staged files / 512 MiB total. The host then forwards `tab.upload.propose` to the extension, which records an unapproved proposal (`uploadPending`) bound to that exact tab, document, snapshot, file-input ref, and file hash — and returns `{stageId, name, size, sha256, pending: true}` to the agent. Nothing is attached to the page yet.
2. **Approve** — the popup shows the pending proposal's project, session, origin, target file input, display path, size, and SHA-256, and requires an explicit, per-file **"Approve this file"** click; there is no bulk or standing approval. Approving is also what prompts for the optional `debugger` permission if it isn't already held. No form is submitted and no automation runs during this step.
3. **Commit** — the agent calls `upload_file` again with the returned `stageId` (no `path`). The MCP process sends `file.commit`; the host re-reads and re-verifies the staged file's integrity (`getStage`), then forwards `tab.upload` to the extension. The extension checks the proposal is still approved and unexpired, re-validates the file input's attributes against the original snapshot, attaches the `debugger`, and calls `DOM.setFileInputFiles` to set the input's value to the staged path — then immediately detaches. **The surrounding form is never submitted and no Enter keypress is sent**; committing only populates the file input, nothing more. **This does not mean the file cannot leave the page.** `DOM.setFileInputFiles` dispatches native `input`/`change` events on the field, the same events a real file picker produces, so the moment the value is set, the page's own JavaScript has the same access a user's manual selection would have granted it — it can read the `File` object off the input, and any listener already wired to that input (or to its enclosing form) can immediately act on it, including issuing its own `fetch`/`XHR` upload with no form submission and no additional user gesture. This is not blocked by same-origin checks, because it is the page's own script acting on its own origin, not a cross-origin access. This bridge does not submit the form or trigger any upload itself, but it also cannot prevent a page that is already scripted to watch for a file-input change from transferring the file out on its own the instant `commit` runs. Only approve a commit for a page and file input you trust to receive that file.

No arbitrary JavaScript, cookies/storage/network access in v2 preview — clicking, filling native form fields, capturing a screenshot, and staging/attaching an `.aab`/`.apk` file are the only interactions offered, each gated by its own separate grant as described above. Interaction and visual consent are distinct from read consent and each expire after 30 minutes; file-upload approval is per-file and does not persist as a standing grant. The agent must ask the user before publishing, submitting, deleting, or other consequential actions; the extension cannot determine the meaning of a page's button, and this bridge does not publish anything to Google Play or any other destination on its own. Page contents are untrusted data. The prototype is not an authentication boundary against malicious programs running under the user's account. Windows and Linux installers are not validated releases yet.

**Prototype status**: the `debugger`-based screenshot and file-upload paths described in this section are newly implemented and have not yet been exercised against a real Brave install — only unit-level logic has been checked. Treat both as unverified until manually smoke-tested (see `extension/SMOKE_TEST.md`). Neither feature, nor this bridge in general, aims for parity with a full in-browser agent integration; the offered operations remain a deliberately narrow, fixed set.

The MCP client (`src/mcp.js`) automatically retries `group_status`, `list_tabs`, and `snapshot` up to 3 times with backoff if the local socket reports `E_DISCONNECTED` — e.g. right after the extension reloads and the native host process restarts. `open_tab`, `navigate_tab`, `click`, and `fill` are not retried: a call made in that same window can fail once with `E_DISCONNECTED`, and the caller must retry it.
