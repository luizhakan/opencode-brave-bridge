# Extension smoke test

**Prototype warning**: steps 8 and 9 below cover the `debugger`-based screenshot and two-phase file-upload paths. Both are newly implemented and have **not yet been validated against a real Brave install** — do not treat them as working until you have run these steps yourself and observed the described behavior. Neither feature aims for parity with a full in-browser agent integration (e.g. "Claude in Chrome"); the bridge's operations remain a deliberately narrow, fixed set. Never claim a feature is verified based on reading the code alone.

1. Run the installer for your platform (`sh scripts/install-unix.sh` on macOS/Linux, or `installers/install.ps1` on Windows) so the native host manifest for `dev.opencode.brave_bridge` is registered. Then load the **installed** `extension/` directory (not the source tree) as an unpacked extension via `brave://extensions` → Developer mode → **Load unpacked**. `manifest.json` ships a static `key`, so the extension ID stays fixed (`gffmhlbhkkgcmjnganoobbnjbplgehdo`) across reinstalls — confirm Brave shows that ID.
2. With the `brave` MCP server configured for OpenCode (the installer runs `opencode mcp add brave --global`), have an agent call the `group_status` tool for a real project/session. Open the popup; the session should appear under **Pending**.
3. Select the pending session, click **Preview proposed origins**, review the listed origins, then click **Confirm read access** and accept Chromium's host permission prompt. `group_status` should now report the session authorized. A new tab group is created with an inactive seed tab; no existing tab is moved, selected, or activated.
4. Verify `list_tabs` and `snapshot` only return tabs inside the granted group and on approved origins. Verify a second project/session, an unapproved origin, and a tab in a different group are all denied. Verify `open_tab` creates a new **inactive** tab in the group. Verify `navigate_tab` works both on an inactive tab and on the group's currently **active** tab, and in neither case does Brave switch focus to that tab or window.
5. Have the agent call `group_status` with `requestClick: true`. In the popup, the session's **Interaction access** section should show a pending request; click **Preview interaction access**, then **Confirm clicks and typing**. Verify `click` now succeeds on a visible element from a fresh `snapshot`, including when the target is the group's active tab, and that reusing the same snapshot/ref a second time fails. Verify `fill` sets the value of a plain text/textarea/contenteditable field from a fresh snapshot without the response ever containing the typed value, and that it is rejected for password, file, hidden, or card/token/email/phone/one-time-code-like fields.
6. With that grant still open, reload the extension from `brave://extensions` (**Reload**, not remove/re-add). Confirm the read grant — and the interaction access from step 5 — come back automatically with no popup interaction, since the tab group, seed tab, and host permission are all still intact. Then close just the seed tab (leave the rest of the group open) and reload again; confirm the grant is silently discarded and the session reverts to **Pending**, since the seed tab's identity no longer matches. Immediately after a reload, a `group_status`/`list_tabs`/`snapshot` call may retry once or twice on its own before succeeding; an `open_tab`/`navigate_tab`/`click`/`fill` call made in that same window can instead fail once with a disconnect error — retry it from the agent.
7. Use **Revoke selected session** and **Revoke interaction access** and verify both are denied afterward. Fully restart the browser and verify every grant (read and interaction) is gone, even though the underlying tab groups remain open. Confirm no bridge operation ever activates or brings focus to a tab or window on its own.
8. **Screenshot (prototype, not yet validated in real Brave)**: have the agent call `group_status` with `requestVisual: true` and a `handle` for an authorized tab. In the popup, the **Screenshot access** section should show the pending request; click **Allow screenshots for this tab (30 minutes)** and accept Brave's prompt for the optional `debugger` permission. Verify `screenshot` on that same handle now returns a JPEG image, that it is well under 500KB, and that it captures the entire rendered page — including any visible iframe content — since screenshot capture is **not** subject to the secret-field masking or text truncation used by `snapshot`. Verify `screenshot` on a different handle/origin, or after the visual grant expires, is denied. Click **Revoke screenshot access** and verify it is denied immediately after. Fully restart the browser and confirm the visual grant and the `debugger` permission are both gone.
9. **File upload (prototype, not yet validated in real Brave)**: use a **synthetic fixture file** (e.g. a small dummy file renamed to `.apk`/`.aab`, well under 256MiB) for this entire step — do not stage or commit a real `.aab`/`.apk` unless the user has explicitly asked to test with that specific file. On a page with a file input, call `upload_file` with `path` pointing at the fixture (no `stageId`) and verify it returns a `stageId` plus `pending: true` without changing the page. In the popup, the **File upload request** section should show that exact proposal's project, session, origin, target input, display path, size, and SHA-256; click **Approve this file** and accept the `debugger` permission prompt if asked. Verify a *second*, unapproved staged file for the same or a different input is **not** committable. Call `upload_file` again with the returned `stageId` (no `path`) and verify the file input's value is set to the fixture and that **no form submission or Enter keypress occurs** — the page must not navigate or show a submission result on its own. Wait for the staged copy's 30-minute TTL (or restart the host process) and verify a stale `stageId` is rejected on commit.

Native host framing is Chromium's 4-byte little-endian length + UTF-8 JSON; the host speaks newline-delimited JSON to the MCP process. Permission prompts must be tested from the popup's explicit button clicks.
